# 总体架构与数据流

## 1. 系统概览

本系统是一个**流水线（Pipeline）架构**，将"多篇新闻文档 → 推理答案"拆成四个可独立开发、可独立评测的阶段：

```
阶段0（输入）      原始新闻文档        Document
   │ 模块1（成员A）事件抽取
阶段1（中间产物）  事件列表            Event
   │ 模块2（成员B）因果识别
阶段2（中间产物）  因果对              CausalRelation
   │ 模块3（成员C）图谱构建
阶段3（中间产物）  因果图谱            CausalGraph
   │ 模块3续（成员C）推理问答
阶段4（输出）      答案                Answer
```

每一阶段的输出都**落盘为 JSON/JSONL**，因此：
- 任何模块可单独调试（喂假数据、单测、人工抽查）；
- 上游改动了，下游产物可直接复用，不必重跑；
- 三人并行开发，通过"文件 + 契约"而非"代码 import 内部实现"解耦。

## 2. 三档难度如何复用同一架构

赛题三档的本质区别是**流水线的起点不同**：

| 档位 | 起点 | 走的阶段 |
|------|------|---------|
| 基础档 | 已给因果图 | 阶段3 → 阶段4 |
| 推理档 | 已给事件列表 | 阶段2 → 阶段3 → 阶段4 |
| 挑战档 | 仅原始文档 | 阶段1 → 2 → 3 → 4 |

编排器 `src/pipeline/orchestrator.py` 根据 `configs/*.yaml` 的 `mode` 字段决定从哪里切入，
推理问答阶段**三档完全共用**。这意味着：只要把挑战档做好了，另外两档"免费"得到。

## 3. 模块职责边界

### 模块1：事件抽取（成员 A）—— `src/extraction/`
- **输入**：`List[Document]`
- **输出**：`List[Event]`
- **要做**：NER、事件触发词识别、事件类型分类、论元角色填充、（可选）指代消解、时间地点归一化。
- **验收**：抽取的事件能对上原文 mention，论元正确，confidence 合理。

### 模块2：因果识别（成员 B）—— `src/relation/`
- **输入**：`List[Event]`
- **输出**：`List[CausalRelation]`
- **要做**：候选对生成（共现/时序）、因果判定（规则/分类/生成式）、关系类型判别、证据回填。
- **验收**：因果对方向正确、类型正确、每条都有原文 evidence。

### 模块3：图谱构建 + 推理（成员 C）—— `src/graph/` + `src/reasoning/`
- **输入**：`List[Event]` + `List[CausalRelation]` → `CausalGraph`
- **推理输入**：`CausalGraph` + `Query` → `Answer`
- **要做**：节点合并、建图、图算法（路径/可达/传播）、三类问答、证据链生成。
- **验收**：答案可解释（有 evidence_chain）、三类问答都通、反事实有对比依据。

## 4. 关键设计决策

1. **证据约束贯穿全链**：`Event.mention` / `CausalRelation.evidence` / `Answer.evidence_chain`
   三层证据使最终答案可追溯到原文，直接回应赛题"基于证据约束"与"可解释性"要求。
2. **关系类型不止 causal**：区分 causal / enables / prevents / conditional，为反事实与态势推演提供更细粒度。
3. **中间产物标准化**：统一 JSON 格式，便于版本管理、人工标注纠错、断点续跑。
4. **推理与抽取解耦**：推理只依赖图结构 + 证据，不依赖抽取模型的内部特征，泛化性更好。

## 5. 扩展方向

- 引入**时序推理**：给边加时间约束（因先于果），做时序一致的因果链。
- 引入**跨文档事件融合**：不同文档的同一事件合并（事件共指），构建跨文档大图。
- 引入**不确定性传播**：置信度沿路径传播，给推演结果概率化。
- 引入**可视化**：把 CausalGraph 导出为 GEXF/GraphML，用 Gephi/前端展示。
